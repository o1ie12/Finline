# Database tables

One Postgres database on Supabase. All access goes through `lib/db.ts`, on
the server, with the service role key. How to build or change the schema is
in [`supabase/README.md`](../supabase/README.md).

**Row level security is on for all 15 tables, with no policies.** That means
the public (anon) key can read and write nothing; only the service role,
which bypasses RLS, can. `supabase/local/build-schema.sh` prints any table
without RLS when it rebuilds the schema. On 2026-11-17 it printed none.

Thirteen tables hold student data. Two do not: `lines` and
`historical_prices`.

Without Supabase settings the app can run on a JSON file instead
(`USE_DEV_STORE=1`, `.devstore.json`). That file has the same tables by name
but no constraints, so it does not prove a query works on Postgres.

## Accounts

### `students` (student data)

One row per student: nickname (`name`), school and grade as the student typed
them, the six-character `access_code` they sign in with, and, if they linked
Google, `google_uid` and `google_email`. Also `points_total`, the old entry
`mode`, the `avatar`, and `profile`, a JSON object the app checks with a
schema (`lib/studentProfile.ts`): savings goal, saved tools, weekly goal, and
the text of their written answers. Used everywhere a student is signed in:
`lib/session.ts`, `app/api/signup`, `app/api/session`, `app/api/auth/google`.

Deleting a student deletes their rows in every table below that has a
`student_id` (cascade), and clears `class_rooms.host_student_id`.

## Learning progress

### `task_results` (student data)

One row per attempt at a task set: the course, the unit, the score, the
attempt number, and `result`, a JSON record of each answer and whether the
student said they were sure. This is the main record of what a student did.
Written by `lib/tasks/submit.ts` (`POST /api/task`). Read by the grades page,
the mistakes folder (`lib/review.ts`) and the weekly goal.

### `module_progress` (student data)

One row per student per unit, with the best score as a percentage and when
the unit was completed. It decides whether a unit counts as done. Written by
`lib/tasks/submit.ts` and `POST /api/progress`. Read by every page that shows
progress (`lib/progressModel.ts`).

### `simulation_runs` (student data)

One row each time a student finishes a course's final: the choices they made
and the outcome, as JSON, with a `kind` that says which simulation or task
set produced it (`lib/sims/types.ts`). Written by `POST /api/simulation`.
The latest run per course decides whether the final is done.

### `line_completions` (student data)

One row per student per finished course. It makes a finished course stay
finished when units are added later. Written by `lib/lineCompletion.ts`.

### `line_tests` (student data)

Optional before-and-after quiz scores per course (`phase` is `pre` or `post`),
with the version of the question bank used. Written by `POST /api/line-test`.

### `daily_activity` (student data)

One row per student per day in Taipei time, counting actions. It feeds the
streak in the life simulation. Written by `bumpDailyActivity` in `lib/db.ts`.

## The life simulation

### `life_game_saves` (student data)

The saved state of a 人生賽局 game as JSON. One solo save per student, and one
per class team (`class_team_id` is `<room id>:<team>`). `updated_at` is also
the concurrency token: a save is refused if someone else saved first. Used by
`lib/lifeGame/` through `app/api/life-game` and `app/api/class/life`. The
solo game is off in production by default (`NEXT_PUBLIC_LIFE_SIM`).

## The AI coach

### `coach_messages` (student data)

The coach's message for one simulation run. Written and read by
`app/api/coach/route.ts`. The message text is generated by a model from the
student's choices.

## The investing replay simulator

### `sim_portfolios` (student data)

One row per student: the dates of their replay, their holdings and cash.
Used by `lib/simPortfolioModel.ts` and `app/api/sim-portfolio`.

### `historical_prices` (no student data)

Real month-end closing prices per ticker. Filled once by
`scripts/seed-historical-prices.ts` from `lib/historicalPricesSeed.ts`. Read
by the replay simulator.

## Class mode

### `class_rooms` (student data)

One row per room a teacher opens: the join `code`, a secret `host_token`, the
course, the status, who opened it (`host_student_id`) and when it was last
used. A room counts as closed 12 hours after `last_active_at`; the app
decides that when it reads the row (`lib/classRooms.ts`). `kind` is `quiz`
or `life`. Used by `app/api/class/*`.

### `class_participants` (student data)

One row per student in a room: the nickname they typed, their score, and
`answers`, right or wrong per question. A quiz room needs no account, so
these rows are not linked to `students`. Deleted with the room.

### `class_join_attempts` (student data, short lived)

Wrong room codes, kept for ten minutes to limit guessing. `ip_hash` is a
salted hash of the network address, or of a device cookie when it starts
with `dev:`. The address itself is never stored. Rows older than ten minutes
are deleted on the next write (`recordJoinMiss` in `lib/db.ts`).

## Reference data

### `lines` (no student data)

The 12 courses: `id`, `slug`, Chinese title, order. The app does not read
this table; course content lives in `content/lines/` and `lib/lines.ts`. It
exists so other tables can point at a course with a foreign key. Its rows are
in `supabase/seed-lines.sql`. A new course needs a row here and an entry in
`lib/lines.ts`.

## Things a new engineer should know

- `simulation_runs`, `line_tests` and `class_rooms` carry both `line_slug`
  and `line_id`. The slug is the older column. See migrations 08, 09 and 16.
- `students.profile` and `task_results.result` are JSON checked in code, not
  by the database.
- Scores for a quiz room come from the student's browser. The server checks
  their shape only.
- There is no table of applied migrations and no automatic backup beyond
  what the Supabase plan provides. Both are in `docs/backend-roadmap.md`.
